# Design 009：求职台插件（审阅草案）

## 产品结构

侧边栏进入「求职台」→ 主表浏览与快速改状态 → 单击整行/公司展开右侧全高详情，右键选择编辑投递信息 → 点击安排时间或通过安排菜单修改笔试/面试。详情顶部「更多」提供同一菜单。只有公司和岗位必填，其余随求职推进逐步补录。

### 字段设计

| 分组 | 字段 | 展示与规则 |
|---|---|---|
| 基本信息 | 公司名称、岗位名称 | 创建必填；主表首列上下两行，支持点开详情 |
| 分类 | 招聘批次、正式/实习、城市、现场/混合/远程、投递渠道 | 详情编辑，主表选择性展示；不从链接或公司推测工作形式 |
| 投递 | 是否投递、投递时间、招聘截止时间 | 是否投递为投递记录派生值；时间未知可留空，截止日可选 |
| 进度 | 当前阶段、关闭结果、偏好星标 | 阶段快速选择；终止原因保留，星标不等于成功概率 |
| 薪资 | 期望薪资范围、币种、日/月/年、薪数 | 主表优先展示；招聘区间和 Offer 数额独立放详情 |
| 笔试 / 面试 | 类型、可自填阶段/轮次名称、安排状态、日期/时刻/精度、地点/线上链接、结果 | 一对多；逐条编辑，主表聚合下一场，已过期节点提示待补结果 |
| 行动 | 下一步、下次跟进时间 | 如「补交成绩单」「确认二面时间」，比单纯状态更容易执行 |
| 资料 | 招聘链接、联系人、简历版本名称、备注 | 详情内；首版只存引用/文本，不将二进制简历塞入 KV |
| 系统 | 创建/更新时间、revision、归档时间、历史 | 用户不用维护；Core 自动记录 |

### 页面布局

1. **页头**：名称「求职台」、当前招聘季/日期、主要按钮「新增岗位」。
2. **概览行**：总记录、已投递、未来 7 天已确认面试、待决定 Offer。仅统计非归档记录，提供精确定义；不放成功率/竞争力分数等缺乏意义的指标。
3. **表格工具栏**：搜索、快速范围（全部/待投递/进行中/已结束），正式版本补充字段筛选、排序和列设置。
4. **表格**：公司+岗位；投递情况+时间；阶段；期望薪资；笔试/面试安排；下一步。不再单列编辑按钮，统一放右键菜单；整行非控件区域也可打开详情，点击下拉框或按钮不误触行导航，右键本身不触发详情。安排时间仍可直接编辑，空值显示「添加安排」。
5. **详情抽屉**：桌面宽度约 480px，从应用内容区域顶部延伸到底部，覆盖在右侧；不按内容高度悬浮、不受来源卡片高度限制，关闭回到原位置。窄窗口使用全宽单列详情。头部与操作底栏不滚动，内容区 `min-height:0` 并独立滚动；短内容仍填满右侧表面，长表单的保存按钮始终可见。未保存编辑关闭时可继续编辑/放弃。
6. **安排编辑器**：类型（笔试/测评、面试）、可手写轮次、日期、时刻、安排状态（预计/确认/完成/取消）、地点与备注；「同时同步岗位阶段」由用户显式勾选。修改一条安排不覆盖其他轮次。
7. **右键菜单**：查看投递详情、编辑投递信息、笔试/面试安排、新增安排、下一步加入任务；在具体安排上打开时提供「编辑这次安排」。位置按应用可见边界避让。菜单与详情更多按钮共用动作，Shift+F10/菜单键可打开，方向键选择、Escape/外部点击关闭，关闭恢复焦点。文本输入保留原生右键菜单。

### 与现有软件的兼容方式（2026-09-08 现场核对）

本轮实际打开本机 AIODashboard 的今天和任务页，并核对当前 `TodayView.tsx`、`TodayTaskCard.tsx`、`TaskCard.tsx`、`TasksView.tsx`、`App.tsx`、`Sidebar.tsx` 与 `styles.css`。前轮演示用两张列表替代宿主页，不能据此判断实际软件布局；本次按观察到的结构重做示意。

| 现有位置 | 当前实际结构 | 求职接入方式 |
|---|---|---|
| 应用壳 | 208px 侧边栏，主内容有自己的滚动区域；Today/插件使用较宽容器，任务页最大宽度 768px | 复用原导航和主题，插件只增加求职台入口 |
| 今天上方 | 问候、快速捕捉、2×2 统计 | 保留，新增关联任务由 Core 的 today_tasks 投影参与正常统计 |
| 今天主体 | 热力图与今日任务占 8/12，右侧重要日/笔记/项目占 4/12 | 保留；求职事项使用后置 extraCards，lg 为 6/12，并非插入现有右栏 |
| 今日任务 | 双列紧凑卡片、渐进填充与圆形打卡按钮 | 使用原 TodayTaskCard 渲染关联任务，完成当日留痕，支持撤销 |
| 任务页 | 日/周/月/年卡、均衡混排/类型分区、进行中/已归档、拖拽及样式菜单 | 使用原 TaskCard；求职行动默认日卡、一次性；增加受控来源入口，完成归档 |
| 投递详情 | 当前 SDK 尚无托管侧栏 | 拟新增宿主侧栏贡献能力，避免把面板塞进 card DOM 而被高度/transform/滚动限制 |

预览只复现布局与关联行为，使用虚构求职数据和示例学习任务，没有读取或修改软件中的真实任务。拖拽、真实热力历史、CLI、重启持久化等须在正式宿主实现后验收，不能由这份示意代替。

### 视觉语言

- 使用宿主 `bg / surface / surface-2 / ink / ink-2 / line / accent` 语义变量，不能给正式插件另建不随宿主变化的硬编码主题。
- 暖纸白背景、白色表格、深灰文字、翡翠绿主按钮；深色自动映射到现有深夜主题。
- 系统中文字体；公司 13–14px，岗位/辅助信息 12px；标题约 24px。数字使用等宽数字特性，日期和薪资便于纵向比较。
- 表格默认行高 64–68px，轻分隔线、无竖向密集网格；悬停轻微提亮；状态使用低饱和底色加文字，不给每家公司随机配彩色标识。
- 状态有颜色也有标签；禁用透明文字造成的低对比。抽屉使用实色表面与克制阴影，动效约 150ms 并遵从减少动态效果偏好。
- 交互稿可调整「舒适/紧凑」和「沿用翡翠绿/蓝色备选」；正式版推荐沿用宿主主题，不把设计调参面板加到产品中。

## 决策

### 决策 1：领域能力在 Core，界面是可启停插件

- **选择**：新增求职领域模型、repository、service；插件通过新的受控 SDK 方法注册独立 View。插件可以关闭、更新、导入，数据仍由本地 Core 管理。
- **理由**：当前 KV 只是通用键值存储，写入不记录领域 activity；将状态转换、统计和历史全部放 JS 会违反本项目业务单一实现与 CLI 平级原则。
- **后果**：第一版需要宿主与插件一起开发、验证；不是一个 ZIP 装到当前旧宿主就能完整运行的纯前端插件。最低宿主版本必须覆盖新增接口。若以后需要完全独立的插件领域能力，应先设计通用扩展机制，不在本功能中偷偷改变架构。

### 决策 2：申请、投递、面试、历史分离

- **选择**：建议 `JobApplication (job_)`、`ApplicationSubmission`、`Interview (jiv_)`；领域历史从统一 activity 的受控 payload 投影或以关联历史实体保存，最终二选一，避免双写两条业务时间线。
- **理由**：同公司多岗位、多批次和多轮面试是正常情况；只有一行可覆盖字段会丢失历史。
- **后果**：列表使用 Core DTO 聚合投递情况、下一场面试和下一步，UI 不自行实现相同规则。数据版本用于检测 CLI/GUI 并发修改。

### 决策 3：区分事实、计划与缺失信息

- **选择**：无投递记录=未投递；存在投递记录且时间 null=已投递但时间未记。面试独立标记预计/已确认/已完成/取消；时间精度为 exact/day/range/unknown。
- **理由**：用户会补录历史，并且招聘方经常只告知「下周面试」；这些不应变成伪造时刻。
- **后果**：准确时刻使用 UTC RFC3339；仅日期/范围需保留原始本地日期语义、IANA 时区和精度，持久化为 UTC 边界区间时不能把边界当作真实预约时刻。复用/扩展 Core 唯一时间入口，不在前端/其他模块重写今日边界算法。

### 决策 4：动作和审计一起成功，显示明确保存状态

- **选择**：创建/状态变更/面试改期等与 activity 在一个存储事务中落盘，提交后 refresh；携带 revision 和 operation_id。失败保持用户输入，可重试；冲突提示载入新版本。
- **理由**：求职记录的丢失、重复投递历史比动画或统计功能更影响实用性。
- **后果**：正式版不以 localStorage 或前端内存为业务数据库；KV 只存列宽、密度、最近视图等可重建的 UI 偏好。

### 决策 5：推荐今天卡片为主，任务按行动关联

- **选择**：建议 V1 同时交付求职台与「今天 → 求职事项」卡片；一次性任务关联作为后续独立切片，用户按具体行动选择加入。此方案为审阅推荐，尚未获用户最终选择或实施。
- **理由**：「面试中」「已投递」是持续状态，不能合理地每天勾选完成；笔试/面试预约和投递截止又需要集中展示。独立卡片便于看时间、公司与招聘进展；任务适合「准备业务案例」「补交材料」等能够完成的行动。
- **后果**：所有展示都读同一求职数据；只有用户点加入任务才生成关联任务。完成材料准备只完成 action，不自动标记面试通过、投递成功或 Offer。只收藏的待投递岗位在未设置计划/截止前不进入每日任务。

### 联动映射（推荐）

| 求职数据 | 今天的求职事项 | 任务卡片 |
|---|---|---|
| 待投递，未安排日期 | 保留汇总数量，完整列表仍在求职台 | 不自动生成 |
| 计划今天投递 / 截止临近 | 显示岗位、计划日与截止日，可直接编辑 | 准备/执行行动由用户选择加入 |
| 已投递，等待筛选 | 仅有明确跟进日期到期才出现 | 不为等待状态生成任务 |
| 已确认笔试 / 面试 | 未来 7 天按时间排序，支持打开/改期 | 备考、材料、复盘按需要关联 |
| 预计笔试 / 面试 | 单列待确认，不能冒充确定时刻 | 可手动关联确认时间的行动 |
| Offer | 显示汇总，决定/跟进日期到期再进入行动区 | 用户选择加入薪酬比较、材料准备 |
| 未通过 / 放弃 / 关闭 / 归档 | 停止未来提醒，保留历史 | 关联未完成项停止提醒，不能记成完成 |

### 决策 6：共享数据与稳定关联 ID

- **选择**：新增 `JobAction`，用稳定 action_id 承载标题、计划日期、完成状态；任务关联表以 action_id 唯一约束绑定 task_id。编辑标题/日期更新同一来源，已完成行动后的新一步创建新 action_id。
- **理由**：只用公司名称/任务标题匹配会在重命名后失效；单纯同时写两份日期容易改期不同步。关联明确后，CLI 与 GUI 也能得到相同结果。
- **后果**：完成、撤销、来源取消、关联创建均需 Core 事务和幂等校验；只处理有关联的任务。不能监听全局 task.completed 就推进所有求职状态，也不能仅依靠应用开启期间的 JS 事件接线。

### 决策 7：使用现有扩展点，补齐缺失契约

- **选择**：求职事项通过 `registerTodayCard` 挂入现有 `extraCards` 位置（热力图/今日任务/右栏之后），建议 size=lg（当前占 12 列中的 6 列），每组限制条数。从卡片打开详情时复用宿主托管的全高编辑器。完整列表导航拟新增受控 `ui.openView`，只允许本插件声明的 View。
- **理由**：目前 TodayCard props 不含 onNav，不能假设从卡片随意切换宿主页面已受支持。现有 `Recurrence::Once` 是每日适用直至完成，插件 createTask 也未暴露 recurrence、来源与计划日期。
- **后果**：行动关联通过新的受限 Core/SDK 用例完成，避免要求插件读写全部无关任务；未来计划的关联任务在任务页可见，Core 的今日投影按来源 action 的计划日期筛选，到期未完成顺延。具体 DTO/权限及对 Today/CLI 的影响在该切片实施前冻结，不在插件 JS 临时隐藏任务来伪装完成。
- **调度**：页面载入、宿主刷新、面板显示时重新查询 Core，并使用 SDK 托管 interval 更新运行中的显示。应用退出不承诺系统提醒；修改安排在下次查询时按最新数据重算。

### 决策 8：宿主承载侧栏与原生任务卡片

- **选择**：全高详情由宿主覆盖层管理，拟提供 owner 绑定的面板打开/关闭贡献能力；UI 内部共用求职详情组件。侧栏按宿主可见内容区域定位，body portal/覆盖层的主题、焦点、滚动锁、错误边界及卸载清理由宿主处理。具体 API 名称需冻结，现有 SDK 的 `react` 并不包含 ReactDOM/Portal。
- **理由**：直接把有最大内容高度的详情放在插件卡片下，会留下空白；把 fixed 面板放进有 transform 的卡片后，也可能相对卡片定位。只有覆盖层的几何边界独立于卡片，首页、任务来源入口和插件页打开才一致。
- **任务兼容**：关联数据进入正常 TaskDayView 后继续走原 TodayTaskCard / TaskCard，不改变其他任务的布局、热力图或拖拽。一次性行动完成即归档，今天仍保留完成态；标题/日期的双向编辑由 Core 的来源用例统一更新，样式/优先级等任务自身属性沿用现有入口。来源导航需受控，不能假设当前 TaskCard 已有任意插件跳转 API。
- **验收**：从滚动后的今天卡片、求职列表与任务来源入口打开，面板上下边缘均对齐；长表单底栏可操作；菜单不被表格 sticky 首列或相邻卡片遮挡；关闭/停用插件后无残留覆盖层或焦点锁。任务完成、归档、撤销、CLI 更新与主题/拖拽无回归。

## 技术落地草图

```text
求职台 React 插件 / dashboard job --json（拟新增）
                 ↓ 参数 / DTO
受身份与 job.read/job.write 约束的插件路由 / CLI 入口
                 ↓
dashboard-core::job_service（校验、状态、统计、历史、日期语义）
                 ↓
dashboard-storage::job_repo（SQL、索引、事务、追加迁移）
                 ↓
SQLite → activity → snapshot::refresh
```

建议插件目录 `examples/plugins/com.leeyl.job-tracker/`，TypeScript + 宿主提供的 React，构建输出单文件 `main.js`，按现有脚手架携带 manifest、README、AGENTS、build 与离线测试。

拟新增的最小 API 分为读（list/get/summary）和写（create/update/submit/changeStage/upsertInterview/archive/restore）；具体方法名称与 DTO 应在 TDD 确认时冻结。目前仅为契约草图，现有 SDK 没有这些方法。

UI 权限按实际贡献点声明 view / today_card / command / settings。求职读写权限需宿主显式新增；今日卡片只查询求职数据，不顺带要求 context.read。任务关联使用拟新增的受限用例，不直接申请全部任务读写权；不申请 note.write / search.read / network。偏好 KV 建议 64 KiB 配额。所有写入 actor 由现有插件会话派生。

首版构建需将所用样式编译进单文件中的插件局部 CSS 并在卸载时清理，或使用宿主已有静态类；CSS 引用宿主变量且只作用于插件根节点。不能依赖宿主运行时编译新的 Tailwind 类，也不能导入第二份 React。

## 红线核对

| 约束 | 落点 |
|---|---|
| SQL 只在 storage | 新 repository 与迁移均位于 dashboard-storage |
| 业务只在 Core | 阶段/投递校验、薪资、日期、统计、下一场面试在 job_service |
| 前端不访问 DB | 仅通过 SDK 与受控 Tauri 包装 |
| activity + snapshot | 每项领域变更写 activity，提交后 refresh；KV 只保存界面偏好 |
| Domain 不依赖基础设施 | 实体、DTO 基础类型和 ID 约定无 tauri/rusqlite/clap 依赖 |
| UTC 与本地边界 | RFC3339 + 精度/时区；local_today_range 为现有权威入口 |
| 追加迁移 | 使用下一个可用 SCHEMA_Vn；不动 V1–V8 |
| JSON 协议 | 冻结公共字段/exit code、升 schema_version、记迁移说明 |
| 不使用 unwrap/expect | 库路径用 CoreError；测试可按项目惯例 |

## 审阅与验收边界

交互稿验证信息密度、表格/编辑器与三个页面之间的演示联动；所有业务仍是内存样本，并未接通宿主数据库和真实任务。正式实现须按 [tasks](tasks.md) 完成 Rust/CLI/SDK/Tauri/插件测试、full 门禁及隔离数据库桌面验证。演示不覆盖完整事务、CLI 变更、重启持久化、并发和通知能力。
