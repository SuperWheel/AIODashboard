# Design 007: 插件平台演进

## 决策 1：保留 v1 同进程模式，明确为 Trusted Plugin

- **选择**：现有 React/WebView 插件继续作为开发模式和受信任本地插件运行。
- **理由**：支持自定义视图和 Vibe Coding，迁移成本最低。
- **后果**：权限桥不是强沙箱；安装 UI、来源提示和安全文档必须明确这一点。未来 Restricted Plugin 使用 RPC，不与宿主共享 DOM。

## 决策 2：能力 API 优先，业务规则仍在 Core

- **选择**：插件只能调用 `api.core`、`api.storage`、`api.events`、`api.ui`、`api.fetch`、`api.log`。
- **理由**：保持 Rust Core 唯一业务实现，GUI/CLI/插件均为客户端。
- **后果**：插件不能直接读 SQLite、调用任意 Tauri command 或修改内置实体结构。

## 决策 3：Manifest 增量扩展，不立即升级协议

- **选择**：新增字段保持 `plugin.protocol/v1` 向后兼容；只有删除/重定义字段才升级协议。
- **理由**：已有 echo/pomodoro 插件可以继续运行。
- **后果**：双端校验器必须忽略未知字段，并在 API 不兼容时明确停用。

## 决策 4：安装采用 staging + 原子替换 + 回滚

- **选择**：先解压到 staging，完成路径、manifest、入口、哈希和版本校验后再替换；保留上一版本。
- **理由**：避免半安装和恶意路径覆盖。
- **后果**：需要记录安装版本、哈希和回滚版本，目录结构会增加 metadata。

## 决策 5：网络由宿主代理并重新校验重定向

- **选择**：插件不能直接使用网络 API；宿主逐跳校验 host、地址、方法、大小和超时。
- **理由**：声明式白名单必须覆盖重定向和 SSRF 风险。
- **后果**：v1 仅支持 GET；后续方法扩展必须增加权限声明和测试。

## 决策 6：注册项统一 disposer

- **选择**：每个 `register*` 返回取消函数，同时宿主按 owner 兜底清理。
- **理由**：兼容 Obsidian 的生命周期思路，避免重载泄漏。
- **后果**：插件作者可以主动清理，宿主仍保证停用后的最终一致性。

## 红线核对

| 架构红线 | 设计落实 |
|---|---|
| SQL 只在 storage | 插件无 SQL API；所有数据经 Core/Repository |
| 业务逻辑只在 core | 插件只编排公开用例，不复制领域规则 |
| 前端禁止直读 DB | SDK 只暴露桥接 API |
| 变更留 activity log | 插件写入、网络、安装、启停均按 actor 审计 |
| 时间统一 UTC | cron 和 Core 继续使用既有时间入口 |
| 迁移只增不改 | 如需 metadata/权限表，只增加新 schema 分支 |
| 库代码禁 unwrap/expect | 新 Rust 库代码使用可传播错误 |

## 风险

- 同进程插件仍可能阻塞 WebView；看门狗只能限制异步加载时间，不能中止同步死循环。
- 公开 SDK 的字段扩展需要严格维护兼容性和类型测试。
- 网络代理的 DNS、重定向和私有地址判断必须在 Rust 侧完成，不能只依赖前端校验。
